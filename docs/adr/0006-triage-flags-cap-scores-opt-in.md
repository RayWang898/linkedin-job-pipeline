# 0006. Triage flags cap scores, but only when the user turns them on

In the maintainer's own setup, the shortlist kept jobs scoring 4 that the user then skipped for three reasons: the level was too high (5 to 7 years, "2+ years PM, 5+ years total", Account Supervisor), the field was one they did not want, or the posting was suspicious (a few lines, no visible employer, a talent agency). The triage model folds level into one score with the other aspects, so it often took off only one point. The hard filters could not fix it: a lower `min_years_exclude` also dropped jobs the user had applied to, `required_years` takes the smallest number in a posting (to allow for alternative requirements), and a minimum description length dropped normal postings.

Decision: the triage call can report four booleans next to the scores: `level_too_high`, `not_interested`, `suspicious` and `interest_match`. The program (not the model) caps every track score at 2 when any of the first three is true, keeps the model's scores in `scores_raw`, records the flags in `flags`, and never marks such a job `needs_custom`. `interest_match` waives `level_too_high`, recorded in `waived`, because the user wants to try a job they are interested in even when it asks for more years. The daily summary lists every capped job and every waived job with the model's reason. Years requirements past the truncation point are sent as `<years_excerpts>`, because a posting often states them near the end.

The engine holds only this mechanism. What counts as each flag is prompt text (`flags_rubric` and the four field descriptions in `prompts.py`, generic in English); a workspace writes its own rules in `prompts.yaml`, and the lists the rules refer to ("Interested", "Not interested") live in `profiles/shared.md`. The whole feature is behind `triage_flags.enabled`, default false; off, the schema, the prompt and the stored results are exactly as before.

Trade-off: this is the kind of silent demotion ADR 0005 removed for visas. The difference is that here the user opts in, writes the rules, and the judgment is about their own preferences, where the cost of a wrong exclusion is lower than a missed sponsorship and a list in the summary makes it visible. A wrong call still hides a job from the shortlist; the user reads the summary list for a few days after changing the rules, and uses `replay_triage.py`.

Ported from the maintainer's old repository (commits `fb4ae5f` and `d7b864e`). Not ported: `replay_triage.py --labeled`, which classified the user's notes with keywords specific to that user; it needs a workspace-configurable rule list first. The cap (2) and the waived flag (`level_too_high`) are constants in `score.py`, not settings, until someone needs another value; `run_daily.py --dry-run` warns when `shortlist_min_score` is not above the cap.
